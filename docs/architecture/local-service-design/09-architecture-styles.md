# §28 架构风格映射

风格不是装饰，是**约束**：每采用一种风格，就必须能指出它落在哪段代码、解决了什么问题、边界在哪、以及哪条不变式（§3）在 CI 里替它站岗。站不住岗的风格就不写进来——下面每一节都按「落点 / 解决什么 / 边界与反例」三问回答，最后 §28.8 给出风格→不变式的总映射。

设计模式层面的落点见 §25（模式是风格的实现手段，不重复列）。

## §28.1 微内核（Microkernel）—— 主风格

**采用，且是全局主风格。** 两侧同构，这是「内核仅 runtime，功能全是模块/插件」的直接落地。

| 侧 | 内核（稳定内环） | 插件（可变外环） |
|---|---|---|
| Go | 5 件事：生命周期编排 · 注册表 · DI 容器 · event bus · Invoke 管线（§4.1） | 能力模块（fs/shell/storage/static/catalog/pluginhost）+ transport 模块（http/ws/mcp） |
| web | 5 段 runtime：契约 · 贡献注册表 · DI · channel 端口 · 模块生命周期与失效隔离（§17.1） | `workbench` 内置 UI 模块 + 外部 UI 插件 |

**解决什么**：加一个工具 = 注册一个 Capability + 写一个前端插件，**内核零改动**（§8.1、§21）。加一条触达面 = 加一个 transport 模块，内核零改动（§4.2）。

**边界与反例**：
- 内核里**不许**出现业务模块名与协议名，CI 双 grep 断言（不变式 7）。
- 「内置」不是特权代码路径：内置模块与外部插件共用 manifest、生命周期、权限闸门，且**都必须可禁用**（§13、§17.1）。工作台一旦挪回内核，微内核就退化成"有插件接口的单体"。
- 反例是把 transport host 放进内核：那样内核就认识协议了，加 MCP 要改内核。本方案改成内核只定义 `Transport` **端口**（§4.3）。

## §28.2 分层（Layered）

**采用，四层，依赖单向朝内。**

| 层 | 内容 | 允许依赖 |
|---|---|---|
| **L0 contracts** | schema、DI token、错误码 | 无（谁都依赖它，它不依赖谁） |
| **L1 kernel** | 上述 5 件事 | L0 |
| **L2 能力模块** | fs · shell · storage · static · catalog · pluginhost | L1、L0 |
| **L3 transport 模块** | http · ws ·（二期）mcp | L1、L0 |

**解决什么**：把"谁能 import 谁"从口头约定变成可断言的规则——L1 不认识 L2/L3，同层零横向依赖（不变式 8、9）。

**边界与反例**：
- 这是**宽松分层**（relaxed layering）：L2/L3 可直达 L0，不强制逐层转发——逐层 DTO 转换是纯税。
- transport 与能力模块**同为插件、不同层**：L3 只做协议编解码 + 调 `kernel.Invoke`，不碰 handler（不变式 2）。
- CI 断言：Go 侧 depguard / `go list -deps`，web 侧 eslint `no-restricted-imports`（不变式 9）。
- 反例是让 L2 模块互相 import "省一次 capability 调用"：两个模块从此必须同时升级、同时禁用，可插拔即失效（§20.6 同理）。

## §28.3 管道-过滤器（Pipe and Filter）

**采用，两处：一条运行期管线 + 一条构建期管线。**

| 管线 | 级 | 产物可独立检查 |
|---|---|---|
| **Invoke（运行期，§9.3）** | recover+trace+deadline → 身份绑定 → schema 校验 → 权限闸门 → 可用性 → 配额/超时 → 审计 → handler | 每级只有"放行/拒绝"两种出口，任一级拒绝即终止（fail-closed） |
| **codegen（构建期，§11.1）** | Go struct → JSON Schema → TS 类型 + zod/ajv 校验器 | 中间产物 JSON Schema 入仓，CI 逐级 diff |

**解决什么**：把"每个 handler 自己记得校验、自己记得查权限"换成**一条有序、集中、可断言**的链——handler 里不再重复边界校验（不变式 2）。

**边界与反例**：
- 模块只能在三个锚点插过滤器：`preAuthorize` / `postAuthorize` / `preHandler`（§9.3 `ctx.Filters()`）。锚点是**枚举的**，不给"任意位置插一脚"的能力，否则管线顺序就不可推理了。
- 过滤器不得跳过后续级——没有 `next()` 之外的短路放行路径。
- codegen 是**单向**的：只有 Go → TS，无回写（不变式 5）。双向 codegen 会把管线变成同步环路，那才是真正的双写。

## §28.4 事件驱动（Event-Driven）

**采用，但严格限定为「进程内通知」，不做事件溯源、不做消息中枢。**

**落点**：
- Go 侧 event bus（§6.3）：模块间无返回值的广播（如 `fs.watch#event`、`shutdown`）。
- 跨进程推送：WS 订阅（§8.2），复用同一条连接。
- web 侧：前端 event bus + `useCapability` 的可用性变化订阅（§20.2）。

**解决什么**：模块间"我做完了你要知道"这类协作不必互相 import——这是不变式 8 的三条合法路径之一。

**边界与反例**：

| 语义 | 取值 | 为什么 |
|---|---|---|
| 投递保证 | **至多一次，可丢** | 每订阅者有界队列（默认 256，`[limits] eventQueue`），满了丢最旧 + 计数 + 发 `#overflow` |
| 发布方阻塞 | **不阻塞** | 慢订阅者不许拖慢发布方 |
| 订阅者 panic | recover 并记日志 | 一个订阅者炸不掉 bus |
| 持久化 / 重放 | **不做**（§26） | 丢了就重查状态；状态真源在 capability，不在事件流 |
| 跨进程 | **不做** | 一期单进程；跨进程走 WS 订阅这条显式路径 |

反例是把事件当**状态真源**（Event Sourcing）或当**请求-响应替代品**：事件可丢，任何"必须到达"的语义必须走 capability 调用。凡是需要返回值的协作，用 capability，不用事件。

## §28.5 客户端-服务器（Client-Server）

**采用。web 页面与 CLI **都是客户端**，本地 Go 服务是唯一服务端。**

| 客户端 | 通道 | 特权 |
|---|---|---|
| 浏览器里的 web 页面 | HTTP（静态）+ WS（JSON-RPC） | 无 |
| `xtools` CLI / AI Agent / 脚本 | WS（JSON-RPC） | 无 |

**解决什么**：**单一状态源**。storage、fs.watch 这类有状态的能力只存在于服务进程里；若 CLI 自己在进程内跑一份内核，就会出现两个进程各持一份状态（§22.1）。同时也让"权限闸门只需写一遍"成立——所有客户端过同一条 Invoke 管线（不变式 2）。

**边界与反例**：
- **没有客户端是特权客户端**：CLI 不因"是本地终端"而跳过 Origin/Host/token 闸门（§9.4）；`CallerID` 由服务端按连接派生，不接受自报（不变式 10）。
- 服务没在跑时 CLI **报错并提示 `xtools start`**，不偷偷起一个后台服务（§22.1）。
- `--local` 是显式例外：一次性进程内模式，且**拒绝**订阅型与独占资源型能力，不静默降级（§22.3、不变式 6）。
- 反例是"本机监听所以安全"：WS 不受 CORS 约束，任意网页可发起跨站连接（CSWSH），DNS rebinding 还能绕过 Host 检查——所以三重闸门硬编开启、无关闭开关（§9.4、§24.2）。

## §28.6 MVC（web 侧）

**采用其分离原则，不采用其经典实现（无控制器类、无双向绑定框架）。** React 侧的实际对应：

| 角色 | 落点 | 约束 |
|---|---|---|
| **Model** | 生成的 TS 契约（§11）+ `IChannel` 拿到的数据 | 唯一数据形状来源，手改即违规 |
| **View** | React 组件（函数式） | **不得 import transport**，只从 DI 拿 `IChannel`（不变式 1） |
| **Controller** | `useCapability` hook（§20.2）、注册的 command（§20.6）、路由 | 交互意图在这里翻译成 capability 调用 |

**解决什么**：把"UI 组件里直接 new 一个 WS 连接"这类耦合挡在门外——换宿主时只换 transport 适配器（§18.2、§19）。

**边界与反例**：
- **导航状态的真源是 URL，不是 store**（§20.5）：`/tool/$containerId[/$viewId]` 两条静态路由即真源，`activeNavId` 这类镜像状态一律删除。镜像 store 是 MVC 里最常见的"第二真源"。
- 前端 schema 校验是 **UX，不是安全边界**（§18.3）；真边界只在 Go 侧。
- 不引入全局 MVVM/状态管理中枢：store 里只留纯 UI 偏好（如 `isSubNavCollapsed`）。

## §28.7 微服务（Microservices）—— 不采用，但保留缝

**不采用。** 场景是**单机单用户**：所有能力跑在一个 Go 进程里，进程内调用无序列化、无网络、无服务发现。拆成多进程/多服务会带来独立部署、版本编排、跨进程调试、可观测性拼接这些成本，而收益（独立伸缩、独立发布、故障隔离）在单机单用户下几乎为零。

**但缝已经在那里**（这是"不采用"与"不可能"的区别）：

| 微服务需要的东西 | 本架构已具备 |
|---|---|
| 明确的服务边界 | capability（`id@major` + Input/Output schema，§7、§7.4） |
| 语言无关的线上协议 | JSON-RPC over WS（§8.2） |
| 契约先行 | Go struct → JSON Schema 已是生成物（§11） |
| 调用侧不感知实现位置 | transport 只经 `kernel.Invoke`；客户端只认 capability id（不变式 2） |

所以将来若真需要拆（例如某个能力要独立伸缩，或四期"外部插件提供后端能力"要求进程隔离），路径是**把一组 capability 搬到子进程、在原位放一个转发 handler**——调用方零改动。四期的子进程隔离（§16）就是走这条缝，且复用同一个 `Transport` 端口（§4.3）。

`// ponytail: 现在拆 = 付全部成本换零收益；缝留着，需求到了再拆`

## §28.8 风格 → 不变式映射

每种采用的风格都必须落到一条可断言的不变式上，否则它只是文档里的形容词：

| 风格 | 守它的不变式（§3） | CI 断言手段 |
|---|---|---|
| 微内核 | 7（内核无业务名、无协议名） | 双 grep `internal/kernel/` |
| 分层 | 9（依赖单向朝内） | depguard / `go list -deps`；eslint `no-restricted-imports` |
| 模块解耦（微内核的必要条件） | 8（模块间零直接 import） | import 边界规则，Go 与 web 两侧 |
| 管道-过滤器 | 2（Invoke 是唯一信任边界） | grep：transport 层不得出现 handler 直调 |
| 事件驱动 | 6（不静默降级：溢出发 `#overflow`） | 单测断言有界队列丢弃与计数 |
| 客户端-服务器 | 10（未握手连接一律拒） | 集成测试：缺 Origin/Host/token 各拒一次 |
| MVC | 1（UI 不感知宿主） | grep：web 业务层零 `platform ===` / `window.__TAURI__` |
| 单一真源 | 4、5 | `go generate` 后 `git diff` 必须为空；触达面清单由注册表派生 |

风格若与不变式冲突，**以不变式为准**——不变式进 CI，风格只进文档。
